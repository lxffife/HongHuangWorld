# 十八层地狱关卡设计草案

> 本文是《洪荒》的游戏化改编方案，不宣称各地民俗、宗教典籍对十八层地狱的名称和排列完全一致。正式剧情以游戏世界观为准。

## 关卡定位

十八层地狱不是酆都城内的普通副本，而是远离主城、由阴司监管的独立刑狱区域。入口设置在幽冥古道尽头；宏观地理预览中与酆都、血海分离。血海归冥河老祖势力范围，地狱的管理权属于后土娘娘统辖下的阴司体系，二者不应混成同一势力或同一地图。

## 核心游玩循环

1. 在入口关隘登记队伍、补给、确认难度与挑战规则。
2. 逐层推进：每层包含环境机制、普通敌人、一个明确目标（击败守狱者/解除封印/护送魂灯/关闭刑具机关）。
3. 每三层设置一个镇魂驿安全节点：恢复、整理战利品、选择继续或撤离。
4. 第 3、6、9、12、15 层设置阶段守关战；第 18 层为终审首领战。
5. 完成终审后开启通关出口与结算；失败时按副本规则返回最近安全节点或入口，不能静默丢失已结算奖励。

## 难度与奖励节奏

- 1–3 层：教会玩家读预警、识别机关、完成一次小队协作。
- 4–6 层：加入镜像与场地控制，第一次要求团队分工。
- 7–9 层：加入高风险移动与周期环境伤害。
- 10–12 层：增加群怪、预警连锁和机关优先级。
- 13–15 层：引入可叠加状态、护送与团队解救。
- 16–18 层：组合此前机制，最终首领不得只靠数值堆血。

奖励应采用服务器权威结算：经验、修为、冥币/冥石、材料和装备均由服务端决定；客户端只展示结果。阶段首领可掉落对应狱层材料，最终首领可掉落稀有制作材料/外观，不应让客户端本地生成可交易奖励。

## 关卡可读性与公平性

- 所有伤害机制先给出清晰预警，再进入判定窗口；预警颜色、形状和音效需能区分。
- 不使用只能靠颜色识别的机关，必须配合轮廓、符文或声音提示。
- 失败条件、复活点、撤离点和奖励保留规则必须在入口说明。
- 安全节点之间避免过长的无战斗空走廊；每层至少有一个可交互目标。
- 首领战阶段切换必须广播服务端事件，客户端特效不能作为伤害判定依据。
- 单人/组队难度、掉线重连、队伍中途加入、奖励归属与副本实例隔离需在服务端实现。

## 当前原型边界

`scenes/EighteenHellsPreview.tscn` 是垂直螺旋布局灰盒，展示 18 个层级、连接坡道、阶段安全节点、入口和终审区域。它没有导航网格、伤害区、机关脚本、怪物刷出、任务状态、服务端副本实例或奖励逻辑。不得把它描述为已经可玩的十八层地狱。

## 下一步实施顺序

1. 先确定每层净尺寸、入口/出口、坡道通行宽度和摄像机遮挡。
2. 将每层拆成独立 PackedScene，定义稳定的 `hell_layer_id`。
3. 制作共享关卡控制器：预警、机关状态、阶段目标、失败/撤离、检查点。
4. 服务端新增副本实例与层级状态权威；客户端只消费状态事件。
5. 完成一层可玩垂直切片，再复制机制模板扩展到其余层。
6. 通过多人测试验证同步、重连、死亡、掉落归属和性能后再开放全部十八层。
