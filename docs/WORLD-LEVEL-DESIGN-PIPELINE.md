# 世界地图制作方案评估与关卡生产规范

更新：2026-11-20
项目：HongHuangWorld / Godot 4

## 一、项目实际类型判断

本项目不是纯 FPS 走廊，也不是格子战棋，而是东方玄幻题材的多人在线第三人称探索/战斗世界。地图需要同时满足：

- 户外大区域：山脉、山谷、河流、荒原、血海岸线。
- 可读的地标：鬼门关、奈何桥、轮回殿、宗门建筑、祭坛。
- 可探索的局部关卡：洞窟、地宫、建筑内部、狭窄通道。
- 大量自然装饰：树木、岩石、枯木、草、残垣。
- 服务端权威的区域、出生点、怪物刷新点、POI、导航与实体 AOI。
- 多人同步与后续区域流式加载。

因此没有任何单一插件适合包办全部地图。应采用混合管线，但只让每种工具负责它最擅长的部分。

## 二、方案比较与最终决策

| 工具/方案 | 最适合 | 本项目决定 | 原因/边界 |
|---|---|---|---|
| Terrain3D | 户外连续地形、山谷、丘陵、海岸高低差、LOD | **主户外地形方案** | 负责地表高度、地形材质、地形网格与地形碰撞；不负责区域规则、POI、实体同步和完整水体玩法 |
| Blender + glTF/GLB | 中式建筑、桥梁、门楼、洞穴模块、独特岩体、道具 | **正式建筑与独特资产主方案** | 模块化、可控美术质量、可复用；碰撞体独立简化 |
| MultiMeshInstance3D | 大量重复树、草、碎石、灯笼等同网格实例 | **运行时/渲染批量化底层** | Godot 原生，不额外引入插件；适合大量相同 mesh |
| ProtonScatter | 编辑器中非破坏式摆放/散布资产 | **候选编辑器工具，暂不进入主项目** | 可加速环境摆放；先锁 Godot 版本并测试导出、地形投射和生成缓存。Godot Asset Library 当前页面将某个 4.2.0 版本标记为 unstable，不能只凭插件名字假定兼容 |
| GridMap + MeshLibrary | 地宫、房间、石廊、规则化模块空间 | **局部副方案** | 适合重复网格模块；不是开放世界地形工具，也不应把自然山野强行格子化 |
| TrenchBroom + FuncGodot | 洞窟、地下城、室内走廊、规则 brush 灰盒 | **复杂室内/洞窟候选** | 能导入 Quake MAP/VMF 并生成网格和碰撞；不适合雕刻连续户外地形 |
| CSG | 玩法比例、碰撞与路线灰盒 | **仅灰盒阶段** | Godot 官方定位是原型/程序化几何工具，不把大量 CSG 留在最终高密度场景 |
| HTerrain | 较小型高度图地形 | **不作为主方案** | 当前项目规划跨区域户外地形，优先统一 Terrain3D；避免两套地形系统并存 |
| WFC/程序化模块生成 | 可重复的地牢、洞穴支路、随机房间 | **后续按需评估** | 需要强约束规则、可控连通性和服务端可复现种子；当前先手工设计关键区域 |

## 三、推荐的组合架构

### A. 户外区域
- Terrain3D：地面高度、坡度、地表材质、地形 LOD。
- Blender GLB：山门、桥、殿宇、石碑、码头、祭坛、洞口等地标。
- MultiMesh：树、草、石块、枯木、灯火等重复物件。
- 水面：单独的水体渲染与服务端水域区域规则；Terrain3D Ocean Mesh 可作为候选视觉底板，但潮汐、漩涡、渡船、落水/阻挡、危险判定不交给地形插件。
- NavigationRegion3D/服务端导航：按实际可行走地面构建；不能只从视觉地形推断可通行。

### B. 建筑和地下区域
- Blender 先制作 1m/2m/4m 模块化建筑套件，按网格原点对齐。
- 普通建筑由 GLB 模块组合，门、柱、梁、屋顶、墙体分开。
- 规则房间/地宫走廊可用 GridMap。
- 复杂天然洞窟或 brush 风格室内可试 FuncGodot + TrenchBroom。
- 交互门、宝箱、机关、怪物刷新点仍使用独立 Godot 场景节点与服务端 ID。

### C. 灰盒到正式资产
1. CSG/简单盒体验证路线、战斗空间、视距和玩家比例。
2. 确认玩法后，替换成 Blender 模块化 GLB。
3. 导入后检查单位、朝向、材质、碰撞和 LOD。
4. 对重复资产做 MultiMesh 或经验证的 Scatter 生成。
5. 在目标设备实际运行并做帧率、内存、碰撞与导航检查。

## 四、地图尺寸与内容生产建议

不以“整个世界一张无限大地形”作为实现目标。使用世界坐标 + 区域/地形分块：

- 世界坐标统一为 1 unit = 1m，X/Z 为平面坐标，Y 为地形高度。
- 初始地形样板建议 1km × 1km 作为内容规划目标，不代表当前已有该尺寸地图。
- 大地图按 Region 展示，户外地形按 tile/patch 加载；区域边界与地形 tile 边界不是同一个概念。
- 关键 POI 和服务端出生/刷新点用稳定 ID，不能依赖客户端节点路径。
- 客户端地形可分块加载/卸载，服务端按玩家 AOI 管理实体；两者生命周期相关但不能混为同一套系统。
- 不能将一个 240m PlaneMesh 改名成大地图；必须真正生成地形数据、碰撞、导航和区域元数据。

## 五、酆都第一张地图的制作顺序

第一张正式样板先控制在一个局部可验收范围，避免先铺满地图：

1. **鬼门关入口区**：门楼、引魂道、两侧山体轮廓、出生安全区。
2. **忘川河谷**：河道、河岸高度差、奈何桥、渡口；桥面与岸边必须真实可走。
3. **轮回殿台地**：抬高地形、石阶、殿宇平台、远景轮廓。
4. **古战场荒坡**：起伏地形、残旗、断兵器、低矮石堆。
5. **血海岸线样板**：黑红色海岸、礁石、血色浅滩、一个可探索祭坛；暂不先做整片深海。

建议第一张样板验收范围约 256m × 256m，作为一块实际地形样板；通过后再扩展到约 1km × 1km 的区域级内容。这个数值是制作目标，不是当前地图事实或最终世界上限。

## 六、血海的专用地形组合

- Terrain3D：海岸高低差、崖壁、滩涂、岛屿地面。
- 独立水面材质/网格：暗红血海表面、流向、涟漪和雾。
- Blender：黑色礁石、沉船/残骸、祭坛、石碑、渡魂码头。
- MultiMesh/Scatter：岸边枯木、骨刺、碎石、稀疏灵火。
- 服务端：血潮阶段、危险区域、漩涡位置、可渡区域、侵蚀状态、资源与怪物刷新。
- 先完成岸线、浅滩和一个 POI，再逐步拓展浅海/深海。不可让视觉水面代替玩法判定。

## 七、版本与资产门禁

- Terrain3D 和 ProtonScatter 都要先确认精确 Godot 版本兼容。
- Terrain3D 是 GDExtension，必须核对操作系统、CPU 架构、渲染器和导出模板。
- Blender 输出 GLB；资源必须保留原始来源、作者、许可证和修改记录。
- 每个静态模型提供简化碰撞；不要对复杂装饰物使用高面数 trimesh 动态碰撞。
- 外部模型必须确认许可，CC0/明确可商用优先；不得把一个资产包的许可套用到同作者全部资产。
- 插件版本锁定到具体 release/commit，禁止直接跟踪 main。
- 插件接入先在独立测试项目验证编辑器、导出、运行、内存和性能，再进入主项目。

## 八、验收标准

- 玩家能从鬼门关安全出生并完整走到奈何桥、轮回殿。
- 地形高度、坡度、碰撞和角色脚底一致，不出现悬空/穿地。
- 地图小图、大图、导航和实体坐标均使用同一世界坐标。
- 区域边界和 POI ID 来自服务端权威元数据。
- 大量植被和碎石不会按每个物件单独创建高开销节点。
- 地形块可独立加载/卸载，不造成玩家、怪物和 POI 的 ID 丢失。
- 远景、遮挡、LOD、阴影和材质在目标硬件上完成性能验收。
- 插件/模型许可随项目保留，导出包不缺 GDExtension 或资源依赖。
