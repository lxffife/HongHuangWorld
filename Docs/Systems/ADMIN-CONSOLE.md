# 后台管理系统实施方案

## 已确认的产品决策
- 与现有 Go 后端同机部署，但作为独立进程和独立监听端口运行。
- 管理范围为全服所有世界、节点和玩家。
- 后台账号与游戏玩家账号完全分离。
- 首个超级管理员通过服务器环境变量初始化；不复用游戏账号。
- 超级管理员创建普通后台用户，并分配角色或细粒度权限。
- 普通后台用户只能使用已授予权限，不能给自己或他人提权。
- 世界实例控制与 WorldServer 进程控制分开授权、分开确认。
- 怪物管理使用独立的数据模型，后续通过版本化配置向游戏服务发布。
- 纳入玩家封禁/解封、强制下线、告警、审计、配置回滚、ChatServer 监控和聊天管理。

## 架构边界
1. Admin Web：独立前端，建议 Vue 3 + TypeScript + Element Plus。
2. Admin API：独立 Go 进程、独立监听地址，复用现有 PostgreSQL，不与游戏客户端 API 混用。
3. Admin Auth：独立后台用户、会话、权限；游戏 accounts 不具备后台权限。
4. Admin Operations Agent：部署在需要控制服务的主机上，只接受经过认证的白名单操作；Admin API 不执行任意 Shell 命令。
5. Game API / WorldServer / ChatServer：后台只通过受控管理 API、心跳和只读查询观察或管理，不成为游戏实时链路的依赖。

## 阶段计划
- P0-A：后台账号、超级管理员引导、会话、RBAC、直接权限授予、密码修改、审计基础。
- P0-B：管理前端框架、登录和主布局、总览页面。
- P1：在线人数、世界/实例状态、节点状态、ChatServer 健康状态、告警。
- P2：玩家搜索和账号/角色/灵魂/轮回/实时位置详情。
- P3：封禁、解封、强制下线和审计查询。
- P4：运维代理、世界实例与 WorldServer 节点控制。
- P5：独立怪物模板、刷新区域和运营配置。
- P6：游戏配置版本、发布/回滚、聊天管理和数据导出。

## 安全要求
- 密码使用 bcrypt 或更强的自适应哈希；不提供密码明文读取。
- 后台会话 token 只存哈希，支持撤销和过期。
- 所有管理 API 默认拒绝，逐路由检查 permission_key。
- 超级管理员角色不可由普通用户授予；至少保留一个可用超级管理员。
- 后台用户创建、权限变更、登录失败、封禁、服务控制和配置发布均写审计。
- 服务控制采用目标白名单、操作白名单、超时、结果回报和二次确认。
- 玩家位置只读取 WorldServer 权威状态；数据库快照必须标记最后更新时间。
- 后台故障不得影响玩家登录、移动、战斗或聊天。

- 迁移 000041：独立后台用户、角色、权限、会话和审计表；超级管理员角色获得完整权限目录。

- 普通用户由后台管理员创建；权限以直接授权方式分配。普通管理员管理权限不能由非超级管理员授予。
