# 总体架构

## 1. 目标

P0 先完成登录、灵魂档案、世界入口、连接权威世界服务器、多人移动同步和断线恢复。第一阶段不实现完整 MMORPG 玩法，也不以高同屏人数作为验收目标。

## 2. 逻辑分层

- Godot 客户端：渲染、输入、UI、本地表现与资源加载。
- Go Backend：账号认证、灵魂/肉身档案、世界目录、服务器发现、连接票据和管理接口。先采用模块化单体。
- C++ WorldServer：实时会话、玩家实体、世界实例、AOI、移动校验和状态快照。
- PostgreSQL：持久化业务数据。
- Redis：短期会话、路由缓存和限时票据辅助数据。
- NATS：后续用于跨进程事件与异步任务；P0 可先完成连接配置，不把关键登录链路绑定到消息总线。

## 3. 网络边界

客户端到业务后端使用 HTTPS/JSON；客户端到世界服务器使用 UDP/ENet。定义独立、带版本号的共享协议。不得假定 Godot MultiplayerAPI RPC 数据包与独立 C++ ENet 服务端兼容。客户端只提交输入或操作意图，服务端验证并产生最终状态。

## 4. 服务端权威

世界服务器负责移动速度/碰撞校验、战斗判定、属性、物品、掉落和轮回结算。客户端不得提交可信的最终位置、物品数量或战斗结果。

## 5. 领域边界

Account、Soul、Character 分离。Soul 代表跨世延续的灵魂档案；每一世创建新的 Character，旧角色及其历史不覆盖。WorldDefinition 是设计数据，WorldInstance 是运行实例，ServerNode 是实际部署节点，三者不能混为一谈。

## 6. 跨世界迁移

采用有状态交接：源节点校验并冻结实体、保存快照；中心服务分配目标节点并签发短时一次性票据；客户端连接目标节点；目标节点验证票据并恢复实体；确认成功后源节点释放旧实体。全流程需要幂等键、过期时间、重试策略和防重复登录保护。

## 7. 可扩展性原则

先做可测试的单世界闭环。AOI、分区、实例数量和同屏人数通过压测决定，不预先承诺超大规模同屏。世界内容使用数据驱动模板扩展，避免每增加一个世界就复制一套服务代码。
